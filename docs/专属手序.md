# 专属手序

自动排键只看这一关自己的砖块，对所有谱一视同仁；专属手序是玩家给某首歌手排的一份，可以分享，社区一起做。两者分开：自动排键的规则不为任何一张谱特化，专属手序是玩家自己的内容，放进文件夹才用。

## 玩家怎么用

1. 进到这首歌（还没按键开始、暂停、死亡画面、通关画面都行；关卡编辑器里要在试玩中），F8 → 专属手序 →「编辑本关手序」
2. 浏览器打开手序编辑器（`Mods/RhythmHint/Editor/index.html`），自动载入这一关：砖块、游戏里正在用的手序、两种自动排法（标准、交替优先）做对照、节拍线、轨道形状、音乐和波形
3. 改完点「保存到游戏」：Edge、Chrome 第一次要选一下 `Mods/RhythmHint/Fingerings` 文件夹，以后直接写进去；别的浏览器会下载文件，按提示放进去。游戏装在浏览器不让网页写的文件夹里时（Steam 默认的 `C:\Program Files (x86)`；Chromium 连同子文件夹都不让选 Program Files、Windows、AppData、ProgramData，2026-11-19 玩家截图「由于此文件夹包含系统文件，无法将其打开」），Mod 让编辑器改存到「文档\RhythmHint\Fingerings」（`FingeringInbox`，选文件夹时从文档打开），每秒把那里的手序搬进游戏的手序文件夹。是搬不是复制：游戏里删掉的手序不会再被复制回来。文件夹里已有同名文件时（2026-11-19 评审：建议名只有「曲师 - 曲名」，同一首歌不同谱师的手序原来会被直接覆盖）：是这一关的手序（认得同一份谱面指纹，或是游戏这一关正用着的那份）就覆盖更新；是另一首谱的或读不出来的，改存成「名字 (2).json」「名字 (3).json」……，编辑器提示另存成了什么名字。编辑器直接写文件夹（`M.saveName`）和 Mod 搬中转文件夹（`FingeringInbox.SaveName`）是同一规则
4. Mod 平时每秒看一次这个文件夹，打歌中（没暂停、没开设置窗口）5 秒一次，有变化就重排，关卡里马上换上。看一次要列文件夹，可能还要搬文件、同步备份，都在主线程上；列文件夹用 `DirectoryInfo.EnumerateFiles`，列目录时就带回大小和修改时间（2026-11-19 复审：原来每个文件单独查一次磁盘，1000 份手序每次 21 毫秒，打歌时每秒掉一帧；现在 0.6 毫秒）
5. 分享：把 `Fingerings` 里的文件发给别人，对方放进同一个文件夹就行。文件里不带音乐
   - 备份（`FingeringBackup`，2026-11-19 评审）：手序文件夹在 Mod 文件夹里，UMM 的卸载、回退（Revert）会把整个 Mod 文件夹删掉（UMM 源码 `UnityModManagerApp/Mods.cs` 的 `UninstallMod`；安装和 Update 只覆盖压缩包里有的文件）。Mod 每次看到手序文件夹有变化就同步一份到「文档\RhythmHint\FingeringsBackup」，启动时手序文件夹整个不见了就从那里还原（日志写还原了哪些）。以游戏的文件夹为准：这次运行里在手序文件夹见过、后来不见了的手序，备份里也删；文件夹还在（哪怕是空的）就不还原。备份文件夹故意不叫 Fingerings，编辑器选保存位置时选到它会提示不是手序文件夹
   - 备份只删「这次运行里见过、后来被删掉」的（`FingeringBackup.Mirror` 的 `seen`；2026-11-19 复审：原来按游戏文件夹整个同步，还原到一半失败时下一秒就把没还原的备份删光，两份游戏安装共用一个备份时也互相删）。代价：游戏关着时在文件夹里删掉的手序留在备份里，以后 Mod 文件夹再被整个删掉时会被还原回来
   - 还原先写待还原清单 `Mods/RhythmHint/Fingerings.restore.txt`（一行一个文件名，`*` 表示备份里的全部），再建文件夹、逐份复制，成功的从清单划掉，全部成功删掉清单；读不了的（杀毒软件在扫、OneDrive 里只在云端的文件此刻离线）留在清单里，下次启动接着还原，在那之前备份里这几份不动。接着还原时同名文件不覆盖，另存成「名字 (2).json」。清单在 Mod 文件夹里，UMM 删 Mod 文件夹时一起删掉，那时整个手序文件夹也没了，照旧完整还原。不用「先还原到临时文件夹再改名」：文件夹里有文件正被别的程序打开时 Windows 不让改名（实测 `FileShare.Delete` 也不行）
   - 还剩的：两份安装里同名、不同谱的手序在备份里仍会互相覆盖；还原只在启动时试
6. 接着改（2026-11-18 用户：很多人一次改不完整张谱就把网页关了，不开游戏很难再找到网页和之前改的东西）：编辑器把每一关现在的样子（每个音符按哪几个键、作者、说明，保存过没有）随时存在浏览器里，关网页、换关卡都不丢，再打开这一关自动接着改，提示条上点「放弃」回到游戏这次给的样子。草稿按砖号记，游戏重新导出时多押分组变了（比如 Mod 更新改了多押规则）也能逐条接上；改过的音符所在那段分组变了、接不上时，提示有几处没恢复，也不再算已保存（2026-11-19 评审：原来按第几个音符记，分组一变整份作废、不提示，改一下就被盖掉）。草稿记着当时的惯用手，切换左撇子后先镜像再套上。草稿还记着打开时那份手序的指纹（`base`：键数、作者、说明、文件名和每个音符的砖号、键，左撇子先镜像成右手再算），存进游戏后另记存进去那份的（`savedBase`）：对得上才自动接上，对不上（打开了别人分享的同一张谱的手序、游戏里换了一份手序）就先问「是否载入」（2026-11-19 复审：原来只按谱面认，打开朋友的手序显示的是自己以前的键位，文件名、作者也变回自己的）。没有指纹的旧草稿：按砖号记、没改过的音符都一样，作者、说明、文件名也一样才自动接上，否则问。游戏每次「编辑本关手序」把那一关另存到编辑器目录的 `recent/`（最多 10 关，同一份谱面只留最新的），编辑器左边「历史」列出这些关卡和各自的进度，点一下带着音乐、轨道预览打开。不开游戏时直接打开 `Mods/RhythmHint/Editor/index.html`（收藏网页，或者 F8 → 专属手序 →「创建桌面快捷方式」在桌面放一个带编辑器图标的快捷方式 `RhythmHint 手序编辑器.lnk`（`ShellLink` 按 MS-SHLLINK 直接写，不开 PowerShell；图标是 `Editor/icon.ico`，用 `tools/make-editor-icon.py` 生成）。不用 .url：路径里有中文时实测打不开；.html 启动页能打开但只有浏览器的图标），先显示最近一关

设置「专属手序」页的「使用专属手序」关掉就全部用自动排键；这一关用的是哪份、有几处对不上，写在同一页的「本关手序」卡片里。

## 怎么认出是哪一关（手序跟着歌走）

只看谱面本身，曲名、文件名都不参与判断（`FingeringMatcher.Choose`）。进关卡时依次：

1. **玩家选过**：这一关（按谱面指纹记在设置的 `FingeringChoices` 里）选过用哪份、或选了都不用，就照选的；文件不在了当没选过
2. **谱面指纹完全一样**：文件的 `charts` 里有这一关的指纹（`CustomFingering.ChartPrint`，按砖块节奏算，算法见「文件格式」）就直接用。同一张谱换文件名、换电脑都一样
3. **按节奏对齐**：谱面更新过时，把每份手序和这一关的砖块对齐，对上 80% 以上、并且比第二名多 10% 以上才自动用
4. **不确定**：有对上 30% 以上但不够确定的（比如同一首歌放了好几份不同的），不猜，设置「专属手序」页的「本关手序」卡片列出候选让玩家选（还有「都不用」，选过以后多一个「重新自动识别」），选了就记住

重复的文件先当成一份（2026-11-19 评审：同一张谱有两份就永远「不确定」），日志写明合并了哪几份：

- 内容一样的几份（键数、惯用手、每块砖、每个音符的键和长按都一样，套上去结果一定一样，比如浏览器重复下载出的「Song (1).json」）只算一份，用 `updatedAt` 新的，一样新就用名字短的
- 第 2 步指纹完全一样的几份里，同一位作者的（去掉富文本标签和首尾空白、不分大小写比 `author`）只留 `updatedAt` 最新的那份。没写作者的不算同一位；最新的有好几份一样新时分不出来，照旧让玩家选

节奏对齐的细节：

- 比的是每块砖「和前一块的间隔、转角、有没有长按」：间隔差 4 毫秒或 3% 以内、转角差 1.5° 以内（有一边读不到转角就不比转角）算同一块。不看绝对时间和砖号，所以改了偏移、中间加删了砖，后面的照样对得上；改了某块砖的角度只影响那一块
- 用最长公共子序列（两串里按顺序都出现的最长那一串，限制在对角线附近的一条带里算，带宽至少 300 块，最多算 3000 万格），只认两边都连续对上至少 8 块的整段：节奏只有几种取值，两首无关的歌零散地也能「对上」一大半
- 对上的砖一样多时，选对不上的段数最少的对法（连在一起的跳过、替换算一段），再一样时依次优先「这一块对应但不算对上」、跳过本关的砖、跳过文件里的砖（2026-11-19 复审：原来平手时先跳过，均匀连打里改了一块砖，前面整段被对到文件的下一块，F J 交替整段反了相位，接缝处多出同轨连按）。只看节奏分不出来的一种：连打里删了一块、后面整体前移、接缝又刚好接得上，错开的位置定在这一串的开头
- 节奏逐块一样（两边砖数一样、第 i 块和第 i 块都在上面的容差内，`Rhythm.SameOneByOne`）就直接一一对应，不再算带状对齐；谱面指纹一样的一定满足，结果和对齐算出的一样（3.5 万块砖、5 份手序进关卡 0.6 秒 → 0.09 秒）
- 对齐前先跳过不可能对上 30% 的文件（`FingeringMatcher.MatchBound`，只是省时间，不改结果）：砖数不到本关 30% 的；本关里落在「文件里有对得上的连续 4 块片段」上的砖不到 30% 的——片段对得上指 4 块的长按一样、后 3 个间隔按对数分桶后桶号各差不超过 1，容差内的两个间隔一定落在相邻的桶里，所以真正对上的砖一块不漏，BPM、节奏取值不同的歌大多在这一步跳过
- 对上的砖用专属手序（作者和玩家惯用手不同时整体左右镜像，长按按比例换成本关的时长），对不上的用自动排键补；一个自动音符只有一部分砖对上时，压在它上面的专属音符也退回自动，保证每块砖正好一个提示
- 有对不上的地方：状态写「有 N 处对不上」，开局在面板上提醒一次（同一首歌、同一个结果重开不再提醒）
- 键数（2026-11-22 起有 6K、8K）：这一关按几键显示由设置定（手动选的，或按估算难度自动选的，见开发说明「6K / 8K」）。
  - 手序的键数和这一关一样：照文件
  - 手序键数更少（偶数键）：同一只手、同一根手指放进来（`KeyLayout.FromLayout`），4K 手序在 6K、8K 里就是中间四个键
  - 手序键数更多、奇数键：不套用。像这一关的（指纹一样，或者对齐能对上 30% 以上）在状态里说明「某某 是 8 键手序，这一关按 6 键显示，未使用」；读文件时 8 键以上、奇数键的日志写一次原因；别的歌的不提
  - 自动选键数时，用上的手序是 4、6、8 键就按它的键数显示（2026-11-22 用户：键数听手序文件的），对不上的地方按这个键数自动排；同一张谱有几种键数的手序时，先只看和难度选出的键数一样的，挑不出来再看全部
  - 1.3.x 的 Mod 读得进 6K、8K 文件（keys 1–16 都收），但只套用 4 键的，不会用错

编辑器打开时，自动补上的音符描黄色虚线，右上角写「N 处待检查」，按 N 跳到下一处；改完保存，新的谱面指纹会加进文件的 `charts`（旧的也留着），以后这一版就直接认出来。

## 文件格式（rhythmhint-fingering，第 1 版）

UTF-8 的 JSON，Mod（`CustomFingering`，读在 `FingeringReader`）和编辑器（`model.js`）各写一份读写。1.3.0 起玩家手里就是这一版；下面写的都是现在代码里的规则，第三方照着写就能和 Mod、编辑器互通。接受、拒绝哪些写法两边一样（只有 Newtonsoft 的几种宽松写法例外，见下），写明「Mod」的是只有 Mod 做的事（比如套用、挑重复文件）。改了会让玩家手里的文件认不出来的东西见「兼容规则」。

```json
{
  "format": "rhythmhint-fingering", "schemaVersion": 1, "keys": 4,
  "song": "曲名", "artist": "曲师", "charter": "谱师", "author": "手序作者", "comment": "说明",
  "leftHanded": false, "charts": ["谱面指纹", …], "updatedAt": "2026-11-18T00:00:00.000Z",
  "以后的版本加的字段": …,
  "hits":  [[砖号, 时间（秒）, 长按（秒）, 转角（度）或 null], …],
  "notes": [[第一块砖号, 最后一块砖号, [[轨道, 长按], …]], …]
}
```

Mod 和编辑器写出来就是这个顺序，hits、notes 一项一行（方便看 diff）；读的时候不看顺序。

### 各字段

| 字段 | 写法 | 读的时候 |
| --- | --- | --- |
| `format` | 文字 `"rhythmhint-fingering"` | 不是就整份拒绝 |
| `schemaVersion` | 整数，现在是 1 | 比读的一方支持的大就整份拒绝（Mod 提示更新 Mod）；没写、不是整数、小于 1 都拒绝 |
| `keys` | 整数 1–16，可省略（当 4） | Mod 能显示 4、6、8 键，键数不同时怎么套用见上一节；`null` 拒绝 |
| `song` `artist` `charter` `author` `comment` | 文字，可省略或 `null`（当空） | 写成数字、数组等整份拒绝。`song` `artist` `charter` `author` 只留前 300 个 UTF-16 字符，`comment` 留 4000，多的截掉。像日期的文字照文字读 |
| `leftHanded` | `true` / `false`：作者按哪只手为主手排的 | 不是 `true` 的都当 `false` |
| `charts` | 文字数组：这份手序认得的谱面指纹 | 不是数组就忽略；不是文字的、超过 100 个字的项忽略；Mod 还去掉重复的、最多认前 10000 个，读完总会补上按 `hits` 算出的那个 |
| `updatedAt` | 文字，ISO 8601 时间（UTC，如 `2026-11-18T00:00:00.000Z`），保存时间 | 写成对象、数组整份拒绝；读不出时间的文字（如 `"yesterday"`）照收。Mod 在同一位作者的重复文件里按它挑新的，读不出时间当最早；编辑器不用它的值，保存时写成当时的时间 |
| `hits` | 数组，1–200000 行 | 见下 |
| `notes` | 非空数组 | 见下 |

- **整数**（`schemaVersion`、`keys`、砖号、轨道）：值是整数就行，`1`、`1.0`、`1e0` 都算 1（2026-11-19 起；1.3.1 及以前的 Mod 只认 `1` 这种写法，所以写文件时写成不带小数点的整数）；`1.5` 这种拒绝。砖号、轨道还要在 32 位有符号整数范围内（−2147483648 到 2147483647），超出整份拒绝
- **数字**（时间、长按、转角）：有限数，`NaN`、`Infinity` 拒绝；长按不能是负数。Mod 和编辑器写的时候时间、长按保留 6 位小数，转角 3 位
- 文件是标准 JSON，最外层是对象（不是对象整份拒绝）。Mod 读的时候额外容忍注释、结尾多余的逗号、单引号、不加引号的字段名（Newtonsoft 的宽松读法，不能收紧），编辑器（`JSON.parse`）不认；写文件的工具不要用这些写法。同名字段取最后一个，JSON 后面多出别的内容整份拒绝
- 文件超过 20 MB 不读。Mod 遇到字段类型不对、数字超出范围的只跳过这一份，设置里列出来、日志写原因，不影响别的手序（2026-11-19 评审：原来 `"format":[]`、`"updatedAt":{}`、超过 long 的大整数会让整个 Mod 停用）

### hits：这一关要按的砖

每行 `[砖号, 时间, 长按, 转角]`，砖号严格递增、时间不减（同一个砖号只能出现一次）。第 4 项可以省略或写 `null`（读不到转角）；第 5 项起忽略（保存时丢掉）。少于 3 项拒绝。

收哪些砖（`FloorHits.From`，游戏里 `GameReader.ReadHits`、离线读谱 `AdofaiLevelReader` 都走它）：

- 砖号是游戏的 `scrFloor.seqID`（离线读谱是第几块砖，起点是 0）。第 0 块（起点）不按
- 不用按的砖不收：自动砖（`auto`，离线读谱是 AutoPlayTiles 打开的那一段）、中旋（`midSpin`，离线读谱是 angleData 里的 999）、假砖（`isFake`）、已销毁的砖（`scrFloor` 为空）
- 长按砖（`holdLength > -1`，离线读谱是有 Hold 事件的砖）：按下后按住到下一块砖，长按秒数 = 下一块砖的时间 − 这块砖的时间。下一块不是长按砖时，它是松开时落上的长按尾巴，不收；下一块也是长按砖时它要重新按一下，照收（游戏里下一块是长按时松开不打下一块，要新按一下）。自动的长按砖不收，它后面那块也是自动落上的，不收。下一块读不到时间（已销毁的砖，游戏里时间记成 0）时长按是 0
- 和 1.3.1 不一样的只有两处，`Compat131Tests` 用随机输入和 1.3.1 逐项比其余的：长按后面紧跟读不到时间的砖（2026-11-19 复审：原来算出负数，这一关「编辑本关手序」打不开，这种关卡以前导不出手序文件）；连续的长按砖（2026-11-20 用户录屏、用户同意改：1.3.3 及以前合成一条长按、后面几块不收，照提示一直按住，过了第二块一拍左右就死）。有连续长按砖的关卡（工坊和 TUF 校准谱 867 张里 15 张）谱面指纹变了，之前做的手序退回按节奏对齐，长按附近改用自动排键
- 时间是砖块的到达时间（秒）。只用相邻两块之差，起点不影响认谱：游戏里是 `scrFloor.entryTime`（里面含「倒计时拍数 − 1」拍，见 `MusicTiming`），离线读谱从第 0 块 0 秒起
- 转角是从上一块要按的砖到这块，星球一共转过的角度（度，180° 是一拍），中间不用按的砖（自动、中旋、假砖、长按尾巴）转的都加进来；第一块要按的砖从起点算起。游戏的 `scrFloor.angleLength` 没有文档、不知道记在离开还是到达那一段，Mod 先按两种对法和砖块时间核对（`FloorHits.CheckAngles`：间隔和「转角 / 180° × 一拍 / 速度倍率」之比和中位数差 3% 以内的算对上），多的那种就是；两种都不到一半就整首不信转角，全写 `null`。从上一块要按的砖到这块之间有哪一块读不到转角（比如已销毁的砖），这块的转角就是 `null`
- 最后按时间排好。上面这套规则的金样例在 `FingeringFormatLockTests.FloorHitsRulesAreFrozen`

### 谱面指纹（charts 里的字符串）

`CustomFingering.ChartPrint`，只看 hits 里相邻两块的时间差、转角和长按，和砖号、曲名、文件名都无关。浮点误差让整体平移后的指纹不一定不变（真实谱整体平移 0.4 秒，866 张里 82 张变了，2026-11-19 复审），所以指纹只对同一组砖块时间稳定，对不上时还有节奏对齐：

1. 每块砖依次写成 `间隔,转角,长按;`：间隔 = 和前一块的时间差 × 1000（双精度浮点，先减再乘）四舍六入五成双取整（第一块写 0）；转角四舍六入五成双取整，`null` 写 `-`；长按秒数大于 0 写 `1`，否则写 `0`。数字不带千分位、不带小数点
2. 全部连起来，按 UTF-8 算 SHA-256，取前 12 个字节写成 24 位小写十六进制
3. 指纹 = `砖数-十六进制`，比如 `9-4ae3b58a876ae199ecc3d8e9`

例：`FingeringFormatLockTests.ChartPrintIsFrozen` 里那 9 块砖连起来是 `0,180,0;62,22,0;125,158,0;0,0,0;62,112,0;62,-,0;250,68,1;1000,360,0;8,3,0;`（62.5 毫秒取 62、22.5° 取 22、157.5° 取 158）。按这段文字独立实现一遍（Python 的 `round` 也是五成双）算出的指纹和 Mod 一致，冻结样例里的两份也一致。

`charts` 由 Mod 生成：「编辑本关手序」时 Mod 按游戏里这一关的砖（没取整的原始时间）算出指纹放进会话，编辑器原样带回文件；作者为更新版再保存时新旧指纹都留着。第三方工具原样保留 `charts`，不要自己往里加：要和游戏读出来的砖完全一样才有用，而文件里的时间只有 6 位小数，按它算出的指纹在间隔恰好落在 x.5 毫秒附近时会和游戏里的不一样（评审 A 的样例：200 BPM、7.5° 倍数转角的 400 块砖，有 38 个间隔取整后变了）。指纹对不上不要紧，节奏对齐照样认得出来（那个样例对上 100%）。

### notes：每个音符按哪几个键

每行 `[第一块砖号, 最后一块砖号, [[轨道, 长按], …]]`，正好 3 项；轨道表里每对正好 2 项（多一项、少一项都整份拒绝，所以以后要给音符加东西只能加新的顶层字段）。

- 按顺序、不重不漏地覆盖 hits：第一个音符从 hits 的第一块开始，「最后一块砖号」必须是 hits 里的砖，下一个音符从它后面那块开始，最后一个音符盖到 hits 的最后一块
- 一个音符覆盖几块砖就是把几块挨着的砖合成一个提示（伪双押、多押）；怎么分组不属于格式，只要满足覆盖规则就行
- 一个音符 1 到 `keys` 个键，轨道 0 到 `keys − 1`、不重复；四键时 0–3 是 D F J K。允许跨手双押（自动排键不会这样排，玩家可以）
- 双押砖（关卡事件 Multitap，一块砖要同时按好几下）：文件里就是一个盖着这块砖、有几个键的音符，hits 不记要按几下，谱面指纹也不算它。
  Mod 套用时（`FingeringMatcher.FitTaps`）盖着双押砖的音符按本关现在一共要按几下补键、减键（最多 `keys` 个）：游戏设置「多次按键方块行为」是「按一次」时双押砖按一下，
  所以在两种设置下做的手序互相拿去用都对。补键先补已有键同一只手的另一根手指，减键先去外侧手指、留惯用手食指；不盖双押砖的音符不动
- 长按：这个键按住多少秒，0 是普通音符。Mod 套用时按比例换成本关的时长：本关这几块砖的长按总和 ÷ 文件里这几块砖的长按总和 × 文件里的长按（谱面改了 BPM 也跟着变）；文件里这几块砖的长按总和是 0 时当 0
- 左右手和镜像：轨道小于 `keys / 2` 是左手（四键：D F 左手、J K 右手；6K 是 S D F | J K L，8K 是 A S D F | J K L ;，每只手从中间往外是食指、中指、无名指、小指）。作者的 `leftHanded` 和玩家的惯用手不同时，Mod 把每个轨道换成 `keys − 1 − 轨道`（四键：D↔K、F↔J），编辑器的镜像也是这个公式。奇数键暂不支持：中间那一轨属于哪只手还没定（编辑器现在算左手），Mod 不套用

### 不认识的字段

- 顶层不认识的字段（以后的版本加的、别的工具写的）：Mod 和编辑器读的时候都原样留下，写回去时放在 `updatedAt` 后面、`hits` 前面，顺序不变（编辑器有一处例外：名字是整数的字段，JS 会把它们排到其他不认识的字段前面）；「编辑本关手序」也把正在用的那份文件里的这些字段放进会话的 `fingering` 顶层，编辑器从那里读回、保存时写回（2026-11-19 起）。不认识的字段加起来超过 25 万个元素（数组、对象、每个值各算一个）时，超出的那个字段 Mod 不留（日志写明，手序照常用）
- 1.3.0、1.3.1 的 Mod 和编辑器保存时会丢掉不认识的字段（之后的版本两边都原样写回），所以新字段必须「丢了也不出错」
- hits 每行第 5 项起忽略；notes 每行、轨道表每对多出来的项整份拒绝

### 兼容规则

- 只加不改：已有字段的名字、类型、含义不改；谱面指纹算法、取砖规则（`FloorHits`）、手序文件夹位置（`Mods/RhythmHint/Fingerings`）不改
- 新东西只加成新的顶层字段，旧版读到会忽略、保存时丢掉，所以丢了也要能用；不往 notes 行、轨道对里加项
- 读的一方只放宽不收紧：以前接受的文件以后也接受（`conformance/reject` 里的样例以后放宽了可以挪进 `accept`，`accept` 的不能挪进 `reject`）
- 写的一方按最严的写：标准 JSON、整数不带小数点、文字不超过上面的长度、砖号在 32 位整数内，这样 1.3.0 起的所有版本都能读
- 只为加字段不升 `schemaVersion`；只有旧版会读错意思的改动才升（升了 1.3.x 整份拒绝，提示更新 Mod）
- 锁住这些规则的测试：C# 的 `FingeringFormatLockTests`（指纹、取砖的金样例；`src/RhythmHint.Editor/tests/fixtures/frozen/1.3.x` 里 1.3.x 实际写出的手序、会话、历史列表，只读、没有重新生成的开关；`fixtures/conformance` 里两边共用的接受 / 拒绝样例和 `expected.json`），编辑器的 `tests/conformance.test.cjs` 跑同一批样例。期望值改了就是破坏性更新。只有 `accept/90`–`93` 这几种 Mod（Newtonsoft）收、编辑器（`JSON.parse`）有意不收的宽松写法（注释、结尾多余的逗号、单引号、不加引号的字段名）两边不一样：C# 断言接受，编辑器测试断言拒绝。
- 2026-11-19 复审加的锁：`Compat131Tests` 把 1.3.1 的手序读取和取砖代码原样放在测试里（`tests/RhythmHint.Core.Tests/Frozen131/`，只能加不能改），现在 Mod 写出的文件、编辑器写法的样例都要被 1.3.1 读进来且内容一致，取砖规则和指纹用随机输入和 1.3.1 逐项比；`FingeringFormatLockTests` 加了像游戏那样累加出来、不精确的时间的指纹金样例（含 x.5 毫秒的间隔），以及乱序、同一时间的砖、自动长按、核对门槛附近的取砖金样例。23 种故意改坏的变异都能被抓到（原来金样例的时间全是 1/16 秒的倍数，「先乘 1000 再相减」这种会让 95/866 张真实谱指纹变掉的改动测不出来）
- 1.3.1 自己读不了共用样例 03（整数写成 `1.0`）和 06（像日期的文字），读 Mod 写的 `updatedAt` 会差本机时区、丢毫秒，这是 1.3.1 的老问题；写文件照「按最严的写」就不会碰到前一种

## 编辑器

`src/RhythmHint.Editor`，原生 JS 加 Canvas，不依赖任何库，双击就能离线打开；随 Mod 装进 `Mods/RhythmHint/Editor`。界面五种语言（默认跟 Mod 的界面语言），深色画布加浮动面板（参考 ComfyUI）。

- 中间是当前手序，左右两列是两种自动排法，和当前不一样的地方亮起来；能对选中的或整首套用
- 左边是小节号、时间和波形，右边是两下之间的间隔（毫秒、几分音符），同一个键 150 毫秒内连按标红（阈值可调）
- 右上是检查器：时间、砖号、前后间隔、来源（专属 / 自动补齐 / 已修改），点键位改键，多押点够个数生效
- 右下是轨道预览（游戏里的砖块路径和星球，跟着播放走）和全曲概览
- 操作：拖动换轨（框选后拖动，选中的音符整体挪；直接按住多押的一个键拖，只挪这个键，2026-11-20 用户截图）；选中后按各轨道的键（玩家自己设的，4K 默认 D F J K，6K、8K 的另外记，2026-11-22）、←→、M 镜像；Ctrl+Z / Ctrl+Shift+Z；空格播放；滚轮滚动、Ctrl+滚轮缩放、空格拖动画面；`[` `]` 设循环；改动自动存草稿（浏览器本地），下次打开同一关自动接着改（提示条上可以放弃）
- 是否已保存按撤销栈顶的那一步比（`History`：每一步一个编号）：保存后撤销、再改别处算没保存（2026-11-19 评审：原来只数步数，这样会显示已保存）。保存要等文件夹权限、写文件：途中又改了或换了关卡，存完只把开始保存时那一步标成已保存，换过去的关卡不受影响；途中改了文件名的保留玩家的新名字；保存途中再按 Ctrl+S、再点保存不再发起第二次（2026-11-19 复审）
- 「放弃」恢复的进度：只把恢复后没再动过的音符改回去，之后又改的留着；改完和打开时一样才算已保存、删掉草稿（2026-11-19 复审：原来无条件标成已保存并删草稿，之后改的那处关网页时不提醒就丢了）
- 待检查（2026-11-19 评审）：自动补齐的音符（`filled`）改过，或选中后按了它现在的键（`confirmed`，记进草稿），就不再待检查；`auto` 表示「还要检查」，每次改动后重算，画布照它画黄色虚线。按 N 或点「下一处待检查」从选中的音符往后找，到结尾从头再来。连按的音符没法用按键确认
- 长按跟着键走：镜像、单独拖一个键、套用参考时，长按留在原来那个键上（和 Mod 的镜像一致）
- 保存：下载文件不算已保存；文件面板可以「更换保存位置」；选的文件夹不叫 Fingerings 时要重选，不记住；记住的文件夹被拒绝权限、找不到时忘掉并重新问
- 草稿：tiles 每项 `[第一块砖号, 最后一块砖号, 键, 改过记 1 否则 0, 各键长按]`（后两项需要时才写），另有 `confirmed`、`fileName`，旧版编辑器都忽略。只留最近 30 关，先删已保存的；浏览器存储写满时先删已保存的再试，还不够就从最久没改的开始删别的关没保存的（正在编辑的这一关除外），每删一份重试一次，最后提示删了几关。别的标签页改了同一关（`storage` 事件）时本页暂停写草稿，提示条让玩家选「载入另一页的进度」或「以本页为准」；别的标签页删掉这一关的草稿（启动时清理旧草稿、点了放弃）不算改了，本页照现状重写，这次写不下也不删别的关（免得两个标签页轮流删对方的）；历史里快速连点只认最后一次。另有 `base`、`savedBase`（见「玩家怎么用」第 6 条）：对不上时提示条问「是否载入」，开着提示条接着改，草稿照常写
- 快捷键：轨道键优先，和 M、N、`[`、`]`、空格、方向键、Home 重复时打开关卡和录键时各提示一次，快捷键面板里也显示；Unity 键名（Keypad4、LeftShift、Alpha1 等）按浏览器的 `e.code` 认；Shift、Ctrl 当轨道键时单独按下再松开才算；录键时忽略组合键；输入框里 Ctrl+S 保存手序
- 打开文件超过 20 MB 不读并提示。读写和 Mod 对齐：砖号在 32 位整数范围、hits 最多 20 万块、文字字段不是文字整份拒绝、名称截到 300 字说明 4000 字、写成 `1.0` 的整数照收、`updatedAt` 写成对象或数组整份拒绝；两边共用样例在 `tests/fixtures/conformance/`。Mod（Newtonsoft）还收注释、尾逗号、单引号、不加引号的字段名，编辑器（JSON.parse）不收，第三方工具不要依赖这几种写法
- 保存时不认识的顶层字段原样写回（放在已知字段后面、hits 前面），文件名规则和 Mod 的 `CustomFingering.SuggestedFileName` 一样（去控制字符、路径符号换成 _、保留名前面加 _、按 UTF-16 截到 80 且不切开 emoji；不是 4 键的再加「 6K」「 8K」）。
  同名文件是同一关、但键数不一样的，和别的谱一样另存「名字 (2).json」，不盖掉 4K 那份（`M.saveName` / `FingeringInbox.SaveName`，2026-11-22）
- 循环：区间短于 50 毫秒不开启并提示（`LOOP_MIN`，原来暂停时按 `[` 再按 `]` 会卡住没有声音）；打拍声排到循环终点加上画面校准对应的那一拍
- 小节号和节拍线用 Mod 推算的音乐拍子（`BeatGrid.Infer`，见 docs/开发说明.md「节拍线和小节」）；右边的几分音符按所在那一拍的长度算（`musicBeat`），不再按关卡 BPM（工坊 2802147583 的关卡 BPM 是 32352 这类数，标出来没有意义）
- 画布：像素比变化（拖到缩放比例不同的显示器）时重新分配画布像素；背景点阵用图案一次铺满；概览尺寸只在大小、像素比变化时测量；轨道卡片隐藏时不画

### 音乐、画面和打拍声

游戏把关卡写进 `Editor/session.js`（`window.RHYTHMHINT_SESSION`；另外两种键数的手序、文件名、键位、自动排法放在 `variants` 里，编辑器左边「文件」里能切换 4K、6K、8K，2026-11-22），同时另存到 `Editor/recent/<Id>.js`（Id 是谱面指纹，6K、8K 后面加「-6k」「-8k」，同一张谱的 4K、6K 各留一份，草稿也按它分开；4K 的和以前一样，2026-11-22），`recent/index.js`（`window.RHYTHMHINT_RECENT`）列出最近的关卡（`SessionLibrary`）。编辑器从本机打开，通过同目录的脚本载入关卡，换关卡时再插一个脚本载入 `recent/` 里的那一份；音乐也放在 `recent/` 里跟着关卡留着，超出 10 关的和没人用的文件删掉，被浏览器占着的留到下次。改到一半的进度存在浏览器里：游戏导出的关卡按这一关的 Id（谱面指纹）存 `rhythmhint.editor.draft.<Id>`；打开的手序文件按 `rhythmhint.editor.draft.<谱面签名>.<文件内容指纹>` 存，两份不同的文件不再共用一份草稿（2026-11-19 复审），旧版按谱面签名存的那份能认出来就接上、迁到新键下后删掉旧的（回退到 1.3.x 的编辑器认不出新键下的文件草稿；游戏关卡的键没变）。草稿里`lanes` 按第几个音符记键位（1.3.1 及以前的编辑器读它，所以一直照写），`tiles` 按砖号记（每项的写法见上面「草稿」一条；2026-11-19 起，有它就按它恢复），另有 `session`（这一关的 Id）、`leftHanded`、`signature`、作者、说明、`fileName`、`confirmed`、`saved`、`changed`、`time`；更早的测试版只记改过的 `{ 音符号: 键 }`，照样认。自定义关卡直接拷贝歌曲，同时另存一份 `<歌曲>.js`（`AudioScript`：`window.RHYTHMHINT_AUDIO` 里按音乐文件路径放 base64），官方关卡用 `AudioDump` 导出 WAV。浏览器在 OGG、VBR MP3 里跳播放位置不准（2026-11-19 用户录屏：暂停、滚动后音画不同步；Edge 实测见验证记录），file:// 下又读不了音乐文件的字节，所以编辑器载入这份脚本后整首解码（`EditorPlayer.decode`），用 Web Audio 从采样里直接放、直接跳（`useBuffer`）；解码好之前、没有这份脚本时（1.3.0 导出的历史、WAV、超过 64 MB 的歌）用 `<audio>`，暂停后原地继续不再跳一次位置。整首解码后自定义关卡也有波形。官方音乐还没载入时，Mod 临时载入音频数据，读完再释放。Mod 能读取采样时会附上波形。对于流式 MP3，Mod 还可用游戏自带的 MP3Sharp 计算波形。本机游戏的 Managed 程序集中没有找到 Vorbis 解码器，流式 OGG 的波形由编辑器解码后补上。导出失败时仍保留偏移、音高和画面校准，手动选择同一首歌也能沿用。

- **关卡偏移**由 `MusicTiming` 计算。游戏导出用 `关卡 offset − 起始一拍 × adjustedCountdownTicks`。`adjustedCountdownTicks` 是倒计时拍数除以倒计时变速倍率。`CalculateFloorEntryTimes` 已把其中的「倒计时拍数 − 1」拍算进砖块时间。离线读谱的砖块没有倒计时，换算为 `关卡 offset − 起始一拍`。四组真实数据在 `MusicTimingTests`，此前九张工坊关卡的离线复核最佳平移均在 ±10 毫秒内。播放中的实测差值只用于写日志对照。
- **音乐和画面**按秒换算。`音乐拍点时间 = 音乐文件位置 − 关卡偏移 − 本歌手动偏移`，`画面时间 = 音乐拍点时间 − 游戏画面校准`。画面校准取自 `scrConductor.calibration_v`，存在 `audio.calibration`，旧会话缺这个字段时取 0。音符、判定线和轨道共用画面时间。波形和概览用同一个换算回到音乐文件取样。每首歌的手动偏移存于 `songOffsets`。音乐的节拍先响就减小，音符先到线就增大。
- **打拍声**跟音乐拍点走，排在和音乐同一条 AudioContext 时间轴上，提前 120 毫秒排声。整首解码播放时，声源从哪个采样、哪个时刻起播是确定的，`renderedBeat` 直接按声源起点和播放速度算出声卡此刻生成的是哪个拍点，不估、不平滑（2026-11-19 评审：原来按画面时间对齐，新声源起播前那段静音被算进去，每次播放、跳转、变速、循环绕回后头几下早 30–60 毫秒，约 1 秒才贴上）。`<audio>` 后备用 `AudioContext.getOutputTimestamp()` 把媒体位置对应到输出采样，平滑相邻帧的几毫秒抖动，浏览器缺少输出时间戳时用可用的延迟估计；从歌曲开头之前开始播时，开头之后的拍子等 `<audio>` 真正走起来再排（`play()` 的起播延迟原来全算成打拍声提前），紧挨开头不到「输出延迟 + 一帧」的那一拍会晚一点。暂停、定位、变速、切换循环或关掉打拍声时清理旧队列。练习变速时音乐的音高随速度改变，避免浏览器保音高处理移动瞬态鼓点。
- **关卡音高**取自谱面设置。编辑器以「关卡音高 × 练习速度」播放，音乐和砖块共用这个速度。例如 75% 音高的谱面选 0.5×，每秒经过 0.375 秒原曲。定位、波形和偏移仍用原曲秒数，旧会话默认 100%。
- **音色**沿用关卡的 `scrConductor.hitSound`。Mod 从 `AudioManager.audioLib` 取已载入的 `snd` 加打击声名字，默认 Kick 对应 `sndKick`，以 WAV 放进会话。开打后也会缓存一份 `Editor/hitsound-名字.wav`，下次开局前就能使用。两处都取不到时编辑器合成打拍声。

在游戏里按 F8 → 专属手序 → 编辑本关手序会重新导出。日志里的「编辑器：偏移 …」列出关卡 offset、起始一拍和倒计时拍数，「编辑器：游戏的画面校准 …」列出单独作用于画面的毫秒数。

- **歌曲数据和波形**：浏览器有 `Uint8Array.fromBase64` 就用它，没有时按 1 MB 一段转成字节，交给解码时不再复制一份；解码后的波形分段计算（`EditorPlayer.waveform`），每帧最多约 3 毫秒，5 分钟的歌约 9 帧算完，算好的部分先显示（原来一次算完，长歌曲载入后画面冻住 0.1–0.5 秒）
- **整首解码排队**（2026-11-19 复审）：一次只解一首；切关卡时还没开始的直接丢掉（排队期间连歌曲脚本都不载入），正在解的解完作废（一首 5 分钟立体声约 110 MB 采样，原来连点几关会几首同时解）。打开关卡、手动选歌都把音乐序号加一，关卡的歌解码回来时序号不对就丢掉（原来刚打开关卡就拖进的歌会被关卡自带的歌换掉）
- **跳转时的画面时间**：`<audio>` 后备跳转刚发出、音乐还没走起来的那几帧，画面停在发出时的目标位置，不读 `currentTime`（防第一次播放时画面跳到 −偏移，即音乐文件第 0 秒；这个现象没复现出来，只在浏览器跳转没生效时才会出现）

### 轨道预览

每块砖按游戏的 `entryangle` 和 `exitangle` 单独绘制，尖角、平头。`PathAngles` 用相邻且未被移动的砖核对角度约定，核对失败时用相邻位置。这样被挪开的砖之间不会多出斜线。

Mod 从 `levelData.Encode()` 取 MoveTrack、PositionTrack、AnimateTrack 事件和相关设置放进 `session.fx`，同一块砖上有带标签（`eventTag`）的轨道事件时，再带上那块砖的 RepeatEvents 和 SetConditionalEvents。`fx.beat` 来自事件所在砖块的速度，用于把事件拍数换算成秒。`trackfx.js` 计算每块砖的位移、旋转、缩放、透明度和出现消失动画，`track.js` 负责绘制。镜头跟着星球，画面高约 10 个单位。缓动采用 DOTween 同名公式和默认参数（Elastic 振幅 1.70158、周期为时长的 0.3，InOut 为 0.45），位移以砖长 1.5 为单位，出现消失的形态与时长为近似。颜色、轨道样式、装饰物和谱面镜头不在重放范围内。

**重复事件**只作用于同一块砖上标签对得上的移动轨道，原事件照常触发一次：

- 按拍（`repeatType` 为 Beat，老谱面不写）：在本砖每隔 `interval` 拍再触发 `repetitions` 次，拍数按本砖的速度换算。
- 按砖（Floor）：往后每隔 `gapLength` 块砖、在星球到达时再触发一次，共 `floorCount` 次，到最后一块砖为止。`executeOnCurrentFloor` 为真时 ThisTile 按到达的砖计算；为假时仍按本砖计算，推迟的拍数由每块砖按自身速度折算。
- 一个事件有几个标签（空格分隔）时取第一个对得上的；`interval` 不大于 0 的按拍重复按砖处理；出现消失动画、PositionTrack 不重复。按拍重复最多展开 10000 次。

依据：编辑器社区文档 adofaieditor.gitbook.io 的 Repeat Events Set-up（原事件之后按间隔再触发，事件须在同一块砖上），以及两份独立的开源重写 AdoCpp（`Level::parseRepeatEvents`）和 Re_ADOJAS（`TimelineManager.ts`，注释称照游戏的 `scnGame.ApplyEventsToFloors` 写）。两者在按拍、按砖、`executeOnCurrentFloor` 上一致；`gapLength` 只有 Re_ADOJAS 处理（AdoCpp 固定隔 1 块），`interval` 不大于 0 的判断也只出自 Re_ADOJAS，这两条可信度中等。Re_ADOJAS 折算拍数时第 0 块、最后一块砖用特殊值，预览一律按砖块时间折算，只在不跟着到达的砖、且涉及这两块砖时有差别。

**条件事件**管的事件只在判定时触发（社区文档 Conditional Events Prep：这类事件在普通情况下不触发）。预览不判定，按全程完美处理：写在 `perfectTag` 里的在本砖照常触发一次（游戏里是判完美的那一刻），只写在失误、失败、过早、检查点等其他判定里的不触发。两份开源重写都没有实现条件事件，这部分是近似。

透明度超过 100%（谱面常写 300%，缓动回弹也会超出）按 100% 绘制：画布的 `globalAlpha` 收到 0–1 以外的值时浏览器会忽略、沿用上一块砖的透明度。过了最后一块砖，中心星球停在最后一块砖上并跟随它移动，另一颗按上一段的转向每拍转半圈。

画一帧时 `TrackFx.tilesNear` 先按出现消失的时刻和每组共用的位移、缩放筛掉画面外和看不见的砖，只给留下的砖计算完整状态。node 下 2 万块砖的谱每帧计算由 2.7 毫秒降到 0.05 毫秒。轨道卡片隐藏时不绘制，也不每帧重设画布；像素比变化时重新测量。

有些谱面把整段轨道藏起来，用装饰物指路。移动轨道把透明度降到 0.12 以下，或把两个轴都缩到原尺寸的 5% 以下时，预览以 16% 不透明度画出砖形，并继续叠加原来的出现消失动画。工坊 3296277169（Avantgarde）的第 392–485 块从谱面约 68 秒起整段隐藏，可以用来复核这段虚影。工坊 3386617648 的第 392 块附近原先也是整段虚影，原因是没有重放重复事件；修正后星球前方的砖逐块飞入，只有身后飘走的砖是虚影。
