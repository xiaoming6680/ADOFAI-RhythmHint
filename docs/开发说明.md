# 开发说明

## 结构

| 目录 | 内容 |
|---|---|
| `src/RhythmHint.Core` | 纯逻辑，netstandard2.0，不引用 Unity：排键参数（`FingeringOptions`）、按间隔排键（`NotePlanner`）、游戏画面缩放（`ViewportShrinker` / `ViewportMath`）、节拍线：从关卡变速和砖块推拍子和小节（`BeatGrid` / `BeatInference`）、死亡后定住的画面时钟（`DisplayClock`）、把游戏歌曲进度摊平成每帧均匀走的时钟（`SmoothSongClock`）、入场 / 出场动画进度（`PresenceAnimator`）、设置页演示谱（`DemoChart`）、哪些砖要按和砖之间的转角（`FloorHits`）、按住中的长按（`Holds`）、界面翻译的查表和回退（`Translator` / `Languages` / `Message`）、专属手序的读写和对齐（`CustomFingering` / `FingeringReader` / `FingeringMatcher`，见[专属手序](专属手序.md)）、交给编辑器的会话和历史（`EditorSession` / `SessionLibrary`）、自动更新（`ModUpdate`）、估算难度（`DifficultyEstimator`） |
| `src/RhythmHint.Mod` | UMM Mod，net48，引用游戏 DLL。Core 的源码直接编进同一个 DLL。`Overlay` 决定画关卡还是演示，`DemoPlayer` 播放演示（有菜单音乐时跟 `scrConductor.songposition_minusi` 和 `bpm` 同步，没有时用音频时钟 + 嗒声），`Lang` + `Languages/*.json` 界面翻译（见「多语言」），`TopBarView` / `LaneView` 绘制（太鼓条只有一条轨道，三押、四押的紫球中间写 3、4，`BallSkin.ChordCount`，设置 `ShowChordCount` 可关；四轨音符有横条和圆形两种样式，圆形和太鼓条共用 `BallSkin` 的球和判定圈画法；圆形的判定点在判定圈圆心，轨道分隔线通到底、一条细线串起判定圈，命中时是判定圈周围的圆形柔光而不是横条那种往上的光柱） |
| `src/RhythmHint.Reference` | **开发专用**：读 Phira（RPE）谱、把谱对齐到关卡、和自动排键逐个比较；离线宽松读 `.adofai`（`AdofaiLevelReader`，难度校准和真实谱面测试用）。Mod 不引用它，游戏里不读任何外部谱面 |
| `src/RhythmHint.Editor` | 手序编辑器：原生 JS + Canvas 的网页，不依赖任何库，随 Mod 装进 `Mods/RhythmHint/Editor`（打包、`-p:Deploy=true` 都带上）。`tests/` 是 node 测试和两边共用的样例，不打包。见[专属手序](专属手序.md)「编辑器」 |
| `tests/RhythmHint.Core.Tests` | Core 和 Reference 的单元测试（xUnit v3） |
| `tools/Preview.cs` | 离线预览：不开游戏，用文字画出某一关的排键；可选给一张自己手排的参考谱做手感对照 |

## 原则

- **每一关只按自己的砖块排键**，不为任何一张谱做特殊处理。参考谱只用来衡量通用规则像不像用户的手法，结果不写回 Mod。
- 每块要按的砖都对应一个提示；`PlannedNote.TileIndex..LastTileIndex` 覆盖它包含的砖（伪多押是几块），测试保证不漏不重。

## 编译

需要 .NET SDK 10 和本机装好的游戏 + UMM（Mod 要引用游戏的 DLL）。

```bash
cp local.props.example local.props
```

然后在 `local.props` 里填游戏目录（或设环境变量 `ADOFAI_DIR`）。

```bash
dotnet test tests/RhythmHint.Core.Tests
```

```bash
dotnet build src/RhythmHint.Mod -c Release -p:Deploy=true
```

`-p:Deploy=true` 会把 `RhythmHint.dll`、`.pdb`、`Info.json` 复制到 `游戏目录\Mods\RhythmHint\`，手序编辑器的网页文件（`src/RhythmHint.Editor` 下的 .html、.css、.js 和 `icon.ico`，不含 `session.js`、`session-audio*`）复制到 `Mods\RhythmHint\Editor\`；不动已有的 `Settings.xml`、手序文件夹和编辑器运行时写的 `session.js`、`recent/`。游戏要先关掉。
装进游戏的是测试版，版本号自动带 `-dev` 后缀（如 `1.3.1-dev`），在 UMM 列表和设置的「关于」里和发布版分开；UMM 解析版本时去掉非数字，当作 1.3.1，检查更新不受影响。要装不带后缀的，加 `-p:VersionSuffix=`。
`Info.json` 由编译生成，版本号只在 `Directory.Build.props` 的 `VersionPrefix` 里改。

## 发布

```bash
dotnet build src/RhythmHint.Mod -c Release -p:UmmPackage=true
```

在仓库根目录 `artifacts\` 生成 `RhythmHint-版本.zip`，里面是 `RhythmHint/RhythmHint.dll`、`RhythmHint/Info.json` 和手序编辑器 `RhythmHint/Editor/`（和 Deploy 复制的是同一批文件，现在 18 个：`index.html`、`editor.css`、`icon.ico` 和 15 个 .js），
可以直接在 UMM 安装器（`UnityModManager.exe`）的 Mods 页点「Install Mod」选它，或拖进窗口安装；也可以手动解压到 `游戏目录\Mods\`。
`artifacts/` 不进仓库。压缩包用 MSBuild 的 `ZipDirectory` 生成，路径分隔符是标准的 `/`；
0.9.1 用 Windows PowerShell 5.1 的 `Compress-Archive` 打包，压缩包里的路径是 `RhythmHint\Info.json`，不是标准写法，不要再用它打包。

同一条命令还会生成 `artifacts\Repository.json`（UMM 的更新清单：版本号和压缩包下载地址）、
`artifacts\update.json`（Mod 自动更新的清单：再加上压缩包的 SHA-256，见下面「更新提示」），并复制一份 `CHANGELOG.md` 到 `artifacts\`。
带后缀的测试包（`-p:VersionSuffix=dev`）只打压缩包，不写这三个文件，免得覆盖发版用的清单；`-p:PackageOutDir=文件夹` 可以把包打到别处。

打正式包（不带后缀、打进 `artifacts\`）之前先检查（`CheckReleasePackage`），不过就报错停下，什么都不写。2026-11-19 评审在版本号还是已发布的 1.3.1 时打包，
静默生成了内容不同的 `RhythmHint-1.3.1.zip` 和新的 `update.json`，传上去的话装着 1.3.1 的玩家不会更新，SHA-256 也和线上的包对不上：
- `CHANGELOG.md`、`CHANGELOG.en.md` 都要有本版本一节，标题写成 `## 版本 · 日期`（如 `## 1.3.1 · 2026-11-19`）
- 两份的「未发布」「Unreleased」下不能还有条目：有就是还没分到版本号的改动，打出来会顶着旧的版本号
- 本地有这个版本的 git 标签 `v版本`（发过 Release、拉取过）时，`src` 和 `Directory.Build.props` 要和标签时完全一样（没提交的改动、没加进 git 的新文件也算）才能重打，
  这时会提示压缩包的 SHA-256 通常和已发布的不同。标签在 GitHub 上建 Release 时才有，新版本第一次打包不受影响；没有 `.git`（源码压缩包）时跳过这一条

带后缀的测试包、`-p:PackageOutDir` 打到别处的包（下面「更新提示」里试自动更新用的假新版）不检查。

发版顺序（2026-11-19 起，1.3.2 第一次照这个发）：装着 1.3.1 及以后版本的玩家一开游戏就会自动装上 latest 那一版，
发出去的包很快到所有人手里，坏包也一样，所以发布前后各加了一道检查，Release 先建草稿再发布。
1. 改 `Directory.Build.props` 的版本号（`VersionPrefix`）；更新记录 `CHANGELOG.md`（中文）和 `CHANGELOG.en.md`（英文）的「未发布」「Unreleased」改成「版本号 · 日期」。
   这一版改了设置字段的，照「设置窗口」里设置文件那一条，往 `tests/RhythmHint.Core.Tests/fixtures/settings/` 加这一版写出的样例，`Frozen/` 加这一版的冻结字段
2. 全量检查：C# 测试、编辑器 `node --test src/RhythmHint.Editor/tests/*.test.cjs`、`node --test tools/planner-js/*.test.cjs`、下面的代码检查四项；
   提交后跑上面的打包命令（漏了第 1 步会被检查拦下）
3. 发布前演练（见下面「发布前演练」）：用上一版原样的代码，让自动更新把 `artifacts` 里这个压缩包装上，重启后是新版本、叠加层和设置窗口正常、设置和手序都在。
   演练出问题就修、重新提交打包、再演练
4. 推送，打标签 `git tag v版本` 并推送标签，建 Release 草稿：

   ```bash
   gh release create v版本 --draft --verify-tag --title "RhythmHint 版本" --notes-file 说明.md artifacts/RhythmHint-版本.zip artifacts/Repository.json artifacts/update.json
   ```

   草稿不算 latest，玩家还收不到。用 `gh release download v版本 -D 临时文件夹` 把三个文件下回来，和 `artifacts` 里的逐个比 SHA-256，
   update.json 里的 `sha256` 也要等于压缩包的；都对上再 `gh release edit v版本 --draft=false` 发布。三个文件一起上线，
   不会出现 Release 已经是 latest、update.json 还没传上去的空档（漏传 update.json 玩家就收不到自动更新）。
   说明照上一版的结构写：引言、分主题的中英对照、安装、升级、国内下载、后续计划、署名，条目和两份更新记录对得上
5. 发布后核对：`仓库/releases/latest/download/update.json` 和 `Repository.json` 是新版本，按 update.json 的 `url` 下回来的压缩包 SHA-256 和清单一致。
   刚发布的几分钟里 `latest/download/` 的跳转可能还是上一版（GitHub 的缓存，1.3.2 实测约 2.5 分钟，响应头的 Date 比发布时间还早），对玩家无害，
   等一会儿再查，或者在地址后面加 `?任意参数` 绕开缓存；
   再把 GitHub 上一版的正式压缩包装进游戏（游戏关着装），开游戏看它从线上自动升级（日志「自动更新：已装好 版本」），重启后是新版本；
   再用 curl 经每个加速镜像（`UpdateMirrors`）取一次 update.json，看是不是新版本（镜像站可能缓存一阵，玩家这边取到的最高版本为准，不影响更新）
6. 夸克网盘和 Q 群文件：传 `RhythmHint-版本.zip` 和 `artifacts\CHANGELOG.md`；群公告写明 1.3.1 及以后的版本重启游戏会自动更新

发出去才发现严重问题时：先 `gh release edit v版本 --prerelease`，再 `gh release edit v上一版 --latest`，latest 退回上一版，还没更新的玩家不会再装上它。
已经装上的不会自动降级（自动更新只往高版本装），所以接着尽快发修好的版本，版本号要比出问题的那一版高；来不及修就把上一版的代码换成更高的版本号发出去。
Release 和标签不删，留着查问题。

### 更新提示

Info.json 的 `Repository` 指向 `仓库/releases/latest/download/Repository.json`（GitHub 跳转到最新一个 Release 里的那个文件），
所以清单只在正式发布后才变，不用提交到仓库。仓库地址只在 `RhythmHint.Mod.csproj` 的 `RepoUrl` 写一处。

- 游戏里的 UMM 读这个清单，版本更高就填 `ModEntry.NewestVersion`（UMM 的 Mods 列表里本 Mod 旁边出现更新图标）。
  UMM 默认（`Params.xml` 的 `CheckUpdates=1`）每天只在第一次启动游戏时查一次：`LastUpdateCheck` 是今天就不查，日志里也没有「Checking updates.」；
  查之前先 ping 8.8.8.8，不通也不查。查到的结果 UMM 不存
- Mod 读这个值（`UpdateNotice`）：一看到就记进 `Mods\RhythmHint\Settings.xml` 的 `LatestVersion` 并写日志，
  当天再开游戏照样提示，装上新版后自然不提示。设置窗口标题栏显示「有新版本」（点了跳到通用页），通用页顶部给下载页按钮
- **自动更新**（1.3.1 起，`AutoUpdater` + Core 的 `ModUpdate`；2026-11-19 用户：Mod 可以联网，要全自动更新，不做签名）：
  启动游戏 5 秒后读 `update.json`（Repository 地址同目录换文件名，见 `ModUpdate.ManifestUrl`），有新版就在后台下载压缩包、核对 SHA-256，
  先整包解到 `Mods\RhythmHint\.update\new`（只认 `RhythmHint/` 下的文件、防路径穿越、必须有 Info.json 和 DLL），旧文件备份到 `.update\backup`，再覆盖过去，
  中途失败从备份还原（2026-11-19 复审：复制到一半失败的那个文件也从备份还原，原来没有的删掉；全部装好后删 `.update\new` 失败只记日志，不算安装失败；协程哪一步抛出都走失败，Mod 关掉时停掉没下完的请求、状态复位，重试能点）。只换压缩包里的文件，设置、手序、编辑器历史不动；下次启动生效。UMM 加载时把 DLL 复制成 `.cache` 再加载，游戏开着也能覆盖原 DLL（实测）。
  查到的版本也记进 `LatestVersion`：UMM 查之前要先 ping 通 8.8.8.8，国内很多网络不通，靠 UMM 很多玩家收不到提示。
  带后缀的测试版（1.3.1-dev）、带后缀的预发布版不自动装；通用页可以关掉（`AutoUpdate`，默认开）；失败时通用页顶部给重试和下载页（国内连不上 GitHub 时从群文件、网盘更新）
- **国内加速镜像**（2026-11-19 玩家日志：自动更新连不上 GitHub；用户选了加速镜像站，不自建存储、不做签名）：镜像前缀写在 csproj 的 `UpdateMirrors`（分号隔开，编进程序集元数据，`AutoUpdater` 运行时读），现在是 ghfast.top、edgeone.gh-proxy.org、ghproxy.net（2026-11-21 起：gh-proxy.com 全部返回 403「Access to proxy rules is forbidden on this hostname」，那家已搬到 gh-proxy.org，换成它的 edgeone 节点）。用法是 前缀 + 完整的 GitHub 地址（`ModUpdate.Sources`，只转 github.com 的地址，file:// 只直连）。
  清单同时问 GitHub 和每个镜像，等都结束（各 20 秒）后挑版本最高的（`ModUpdate.Newest`：镜像站可能缓存着旧清单）；压缩包先从给出清单的来源下，下不了或 SHA-256 不对再按顺序换（`ModUpdate.FirstThen`，每个 120 秒）。日志「自动更新：查到 版本（github.com …; ghfast.top 1.3.2; …）」写着每个来源的结果。
  镜像站是第三方，清单和压缩包都经过它，理论上能换包（用户接受）；会失效，失效了改 `UpdateMirrors`，加之前用 curl 试 `前缀https://github.com/xiaoming6680/ADOFAI-RhythmHint/releases/latest/download/update.json` 要拿到最新清单、压缩包哈希一致、不存在的文件要返回 404（2026-11-19 实测这三个都对，gh.llkk.cc、github.moeyy.xyz 连不上）。
  1.3.2 及以前的版本只连 GitHub（已发出去的改不了），连不上 GitHub 的玩家要手动装一次带镜像的版本
- 试自动更新：`-p:UmmPackage=true -p:VersionPrefix=9.9.9 -p:PackageOutDir=别的文件夹` 打一个假新版，把那里的 update.json 里的 url 改成 `file:///…/RhythmHint-9.9.9.zip`；
  游戏关着时用 `-p:Deploy=true -p:VersionSuffix= -p:ModRepository=file:///…/Repository.json` 装一个不带后缀的版本，开游戏看日志「自动更新：已装好 9.9.9」。
  试完删掉 Settings.xml 里的 `LatestVersion` 和 Mod 文件夹里的 `.update`，再正常装一次
- **发布包和 update.json 的约定不能改**：1.3.1 → 下一版这一跳永远由 1.3.1 已发布的安装代码执行，所以发布包只能有 `RhythmHint/` 下面的文件、必须有 Info.json 和 RhythmHint.dll；update.json 的 `format`、`version`、`url`（https）、`sha256`（64 位十六进制）四个字段和 `releases/latest/download/update.json` 这个地址都不能变。`ModUpdateTests.TheReleasedInstallerStillInstallsTodaysPackage` 照 csproj 的打包逻辑在测试里打包，交给 v1.3.1 原样的安装代码（`tests/RhythmHint.Core.Tests/Frozen/ModUpdate131.cs`，只能加不能改）装一遍
- UMM 安装器的 Mods 页读同一个清单，右键「Update to 版本」按 `DownloadUrl` 下载压缩包并安装
- 漏传 `Repository.json` 不影响安装，只是玩家收不到提示；没联网、国内连不上 GitHub 时也只是不提示
- 1.1.0 及更早的版本 Info.json 里没有 `Repository`，收不到提示

## 排键规则

### 规则（1.0.0，`NotePlanner`）

2026-11-16 玩家反馈手序不对，调研了原版和同类 Mod（下面「参考」），用户决定按 LaneReader「时间重置法」的思路改。
每一下按哪根手指只看和前面几下的间隔，不看 BPM、小节、拍点，也不切段。R = 主手重置间隔（`ResetWindow`，默认 130 ms：2026-11-19 从 165 ms 改，依据见[排键算法说明](排键算法说明.md)，老设置里还是 165 的由 `Settings.MigrateDefaults` 改一次），主手是右手。

1. **合成时刻**（多押，2026-11-17 改，见第 11 条）：相邻两块转角 ≤ 30°、相隔 ≤ 60 ms 算同时按，一块接一块串成双押、三押、四押；
   连成 5 块以上是连打，全拆开。读不到转角时退回旧规则：和这一组第一块相隔不到 35 ms。
2. **单押的状态表**（上一下用的手指 + 间隔 d；右手最后一次按到现在 dRight）：

   | 上一下 | 条件 | 这一下 |
   |---|---|---|
   | 没有 / D / 左手双押 | — | J |
   | J | d > R | J（慢：一根手指点得过来） |
   | J | R/2 < d ≤ R | F（左右食指轮流） |
   | J | d ≤ R/2 | K（太快：右手两根手指轮指） |
   | K / 右手双押 | d > R | J |
   | K / 右手双押 | d ≤ R | F |
   | F | d ≤ R/2 或 dRight ≤ R | D（右手刚轮过，左手也轮） |
   | F | 否则 | J |

   所以均匀的连打（默认 R = 130 ms，2026-11-19 从 165 改，依据见排键算法说明）：> 130 ms 是 `J J J`，66–130 ms 是 `J F J F`，≤ 65 ms 是 `J K F D` 循环；停下来（> R）总是回到 J。
   关掉轮指（`UseRoll`）时 K、D 两行都换成食指交替。
3. **外轮**（`OuterRoll`，默认开）：轮指出来的外侧手指和它前一下（同一只手的食指）换位置，`J K F D` 变成 `K J D F`（用户习惯的 4312）。换了会连按的不换。
4. **双押优先右手**：放 J K，右手上一下刚按过（< 150 ms）才放左手 D F。
5. **右手专心按双押**（`ChordFocusWindow`，默认 450 ms）：用户试打反馈「J 单押 → J+K 双押 → J 单押」右手食指、中指配合不过来。
   紧挨着双押（前一下或后一下就是双押）、隔得不超过 450 ms 的单押放另一只手（双押在右手就放左手食指 F，F 刚按过才用 D）；
   前后都是双押时看离得近的（一样近看后面的）。中间的单押照常排。
   第一版把双押前后 450 ms 内的单押全放左手、F D 轮流，用户随即反馈「不要有 21 式，尽量避免从内向外的楼梯」，改成只换紧挨着的那一下。
   让不开的只有「左手双押和右手双押中间夹一个单押、左右手都刚按过」这种。
6. **不出现食指→外侧手指**（用户：不要有 21 式，尽量避免从内向外的楼梯）：同一只手先食指再外侧手指（F→D、J→K）挨得近（≤ R）时：
   - 外轮换不了顺序（换了会连按，通常是前后夹着让手的单押）：这一下改按另一只手的食指，左右手轮流
   - 下一下要让给左手食指、又挨得不到 150 ms：这一下先用 D，下一下再按 F（从外向内）；双押在左手时（见 10）反过来，先用 K 再按 J
   本机 12 张关卡上 ≤ 165 ms 的 F→D、J→K 都是 0；还剩少量 187–300 ms 的「一下 J，隔一会儿接 K J D F 轮指」开头。
7. **连按**：同一条轨道连续按两下至少隔 150 ms（`JackWindow`）；规则排出来会连按时（多半紧跟在双押后面），换到离上一下最近的空轨道。比较时带 1e-6 容差。
8. **双押只能是同一只手**：轨道 0+1（D F）或 2+3（J K），**绝不跨手**（冰与火玩家的硬性要求）。
   三押必然用到两只手：按双押的那只手按两个键，另一只手的食指补一个（食指刚按过、会连按才用外侧手指）；四押四个键全按（第 11 条）。
9. **左撇子**（`LeftHanded`，设置里的「惯用手」，2026-11-16 用户要求）：上面 1–8 按右手为主手排完后，整体左右镜像（轨道 i → 3 − i，D↔K、F↔J）。
   于是慢的左手食指 F 连点、停下回 F、双押优先 D F、紧挨着双押的单押放右手、轮指 D F K J；双押同手、不出现食指→外侧手指这些约束镜像后照样成立。
   规则只写一份，左右手永远一致（测试 `LeftHandedIsTheMirrorOfRightHanded` 在随机谱上逐个音符核对）。
   `tools/Preview.cs` 的「跳轨」统计双押时只取编号最小的轨道，所以镜像后数字会略有不同（某关右手 8/504、左手 14/504），排法本身是对称的。
   试验台 `tools/layout-lab.html` 的 `planMod` 只做右手为主（默认），没有加左撇子。
10. **多押用另一只手**（`ChordsOnOtherHand`，设置里的「多押用手」，原名「双押用手」，2026-11-17 玩家反馈「双押用手和惯用手分开设置」）：
    按右手为主手的坐标写，第 4 条改成「双押优先左手 D F，左手刚按过才放右手」；第 5、6 条跟着换边：紧挨着双押的单押改用右手 J，
    下一下要让给 J 又太近时这一下先用 K。左撇子再整体镜像，所以四种组合只有这一份规则。
    存的是相对惯用手的选择（同惯用手 / 另一只手），默认同惯用手，老设置读进来排法不变。
    本机关卡 life（878 个双押）：双押右手 / 左手从 519 / 359 变成 359 / 519；停顿后第一下是单押的 95 次里主手起手 78 → 92；
    「跳轨」46.8% → 60.5%，因为左手双押取轨道 0、后面接右手 J 就算跳了两条，是这种手法本身的样子。
    试验台的 `planMod` 加了同样的开关，和 C# 在 200 张随机谱、两种设置共 80000 个音符上逐个一致。

11. **多押怎么认**（`ChordAngle` 默认 30°、`ChordMaxGap` 默认 60 ms，2026-11-17）：用户要识别三押、四押（Timeline 里有），
    玩家反馈旧版把快速轮指段识别成双押。旧规则只看时间（和第一块相隔 < 35 ms），两头都错：
    - Timeline 的三押是 180 BPM 下 15° + 15°（每块隔 27.8 ms，跨 55.6 ms），第三块进不了 35 ms，画成双押 + 单押；120 BPM 下 15° 的双押是 41.7 ms，也合不上。
    - life 里 1816 BPM 下 180°、908 BPM 下 90° 的连打每块只隔 33 ms，被合成一串双押。
    谱师画多押用的是很小的转角，快连打转角正常、只是 BPM 高，所以改成看转角（游戏里读 `scrFloor.angleLength`）。
    在本机创意工坊和本地共 37 张关卡上比较（分析脚本没进仓库）：

    | 分法 | 合出的多押 | 其中其实是均匀连打的 | 小转角（≤15°）多押没合上 |
    |---|---|---|---|
    | 旧：和第一块相隔 < 35 ms | 9007 | 4220 | 92 |
    | 转角 ≤ 30° 且 ≤ 60 ms（现在） | 4769 | 7 | 3 |
    | 只看节奏（比前后都挤一半以上） | 4944 | 0 | 10 |

    只看节奏会把连打里加倍速的小快段（1/16 里夹 1/32）当成三押，所以不用。转角上限 45° 时误合 29 处，20° 时多押只剩 289 个（大多数伪多押用 30°）；
    间隔上限取 45 / 60 / 80 ms 结果几乎一样。用瞬间超高 BPM 做的伪多押（转角大、间隔极小、前后都空）在这批谱里一处也没有。
    转角先和砖块时间核对（`FloorHits.CheckAngles`：间隔 ≈ 转角 / 180° × 一拍 / 速度倍率）。`angleLength` 记的是离开还是到达这块砖的转角没有文档，
    两种对法各算一遍，看多少对相邻砖块和中位比值相差不到 3%，用多的那种；都不到一半就退回只看时间，日志里写出两种对法各对上多少。
    比较转角时留 0.1° 余量（`NotePlanner.AngleTolerance`）：游戏里方向存成单精度浮点，30° 读出来是 30.000004° 或 29.999996°。
12. **长按换手接**（2026-11-20 用户实测：连着的长按排在同一个键上「单手几乎不行」）：上一下的长按到这一下还没松开（连续的长按砖，
    或长按后面紧跟一块中旋、中旋和下一块同一时刻），这一下换另一只手：单押用那只手的食指（刚按过才用外侧手指），多押把按着的键算作用不了
    （`Blocked`），双押自然放另一只手、三押补键避开它。游戏里接力那一下按下后只认新按的键，前一块的键随时松开都行，所以换手接不用掐着时间松手；
    同一个键要在前一块最后一点松开再按，松早了就死。外轮（第 3、6 条）为了不连按换手时，也不换到接力的那只手上（TUF 3303 的 3260、3261）。
    工坊和 TUF 校准谱 867 张逐音比较：只有有长按的 17 张变了，每种设置约 172 个接力的音符换了手，没有长按的谱一个音符都没变；改后接力仍在同一只手的是 0。
13. **双押砖**（关卡事件 Multitap，游戏里 `scrFloor.tapsNeeded`；2026-11-20 用户：RJ-X 的紫色双押方块被识别成单键）：一块砖要同时按好几下，
    游戏里没按够不前进（`scrPlanet` 每按一下 `tapsOnThisFloor++`，不到 `tapsNeeded` 闪一下就返回）。`TileHit.Taps` 记要按几下，
    合成时刻时这块砖占几个位置（第 1 条），所以它和伪多押一样排：两下是同一只手的双押，三下是三押；连着的几块加起来超过 4 下照旧按砖拆开，
    一块砖自己最多 4 个键。游戏设置「多次按键方块行为」改成「按一次」（`Persistence.multiTapTileBehavior = HitOnce`，第一下就前进）时 `Taps` 是 1，
    照普通砖排；这个设置算进关卡指纹，改了马上重排。工坊和 TUF 校准谱里没有用它的；游戏自带的 RJ 世界几关（5 张离线对照）57 块双押砖全是 J K。
    专属手序套用时见 [专属手序](专属手序.md)「notes」一节。
    第一版只看比值中位数、只留 0.000001° 余量，用户在 Timeline 里截到三押画成单押 + 双押、四个单押。实机日志确认 Timeline 按离开对上 100%、按到达 58%，
    即 `angleLength` 记的是离开这块砖的转角，问题出在浮点误差；加余量后游戏里是 847 个提示、三押 104、四押 5，和离线预览一致。
    两种对法的核对仍然每关都跑，转角万一对不上（游戏改了字段含义）会退回只看时间。
    Timeline 现在是三押 104 个、四押 5 个；life 的双押从 867 个降到 509 个，「两个多押挨得太近」从 520 处降到 256 处。
    试验台的 `toMoments` / `planMod` 同步，和 C# 在 240 张带转角的随机谱（含 1388 个三押、1465 个四押）共 84680 个音符上逐个一致；
    试验台自己读 `.adofai` 的结果和 Preview 导出在 Timeline、life 上逐块一致。

14. **6K / 8K**（2026-11-22 用户：6K = S D F J K L，8K = A S D F J K L ;，每只手从中间往外食指、中指、无名指、小指，不用拇指）：
    `KeyLayout` 是按键数的键位（左边一半左手，`FromLayout` 按同一只手、同一根手指换算轨道）。`Keys` 大于 4 时走另一套排法 `PlanManyKeys`（`NotePlanner.ManyKeys.cs`；
    同一天用户看了第一版说「怎么那么多全照搬四 K」，让参考网上多键的手法另写，4K 不能动）。只共用 4K 的 `Moments`（多押怎么合，提示的个数、每个提示盖哪几块砖和 4K 一样）、`FocusChords`、`Blocked`、长按接力：
    - 慢（和上一下隔得超过 R）右手食指；中速（R/2–R）换另一只手的食指，左右食指轮流
    - 快连打（`FastRuns`：相邻间隔都不超过 R/2 的单押；让手的单押、上一下长按还没松开的不进）：先在一只手上从外往内滚到食指（外轮关掉时从内往外），
      这只手的手指都用过一遍还没完才换另一只手，再长两只手整手轮流（6K `L K J S D F`，8K `; L K J A S D F`），最后不够一只手的从食指往外数。
      2026-11-25 用户：轮指少换手、尽量在一边轮完、不要跨越中间；原来每组是一串的一半（两下 J F、四下 K J D F，都跨中间），给用户看了「一只手用完再换」和
      「每根手指歇够 130 ms 就一直在一只手上循环」两种，用户选前一种（长串里能在一只手上循环的只有约两成，见验证记录）。
      前一下在 R 以内就从另一只手起，否则右手起；轮指关掉、交替优先的短串只用两根食指
    - 起手挑选（`RunLanes`）：两只手起手各一种，最后一组只有一下时还可以把它改到中指；起手和上一下连按的不要，
      其余按「每有一下手指歇不到 R/2 又按 20（只用食指时不算）、最后一下占了紧接着的让手单押要用的食指 12、起手同手 21 式 10、上一下变成孤立音符 5、
      改用中指 3、不是顺着起手 1」挑最小的。「尽量在一边轮完」：一只手上怎么排都有手指歇不够时（紧跟多押、密集单押，刚按过那只手），
      再按原来每组一半的分法挑一次，分数不比一只手差就用它（只看一只手时，Hello (BPM) 2023 那段双押后 15、15、30、30 ms 的单押会让 K 隔 30 ms 又按，
      `FingersRestBetweenChordsAndShortRuns` 守着）
    - 多押（`ManyChordHand`、`BuildManyChord`）：手指够就整组放在一只手上，从食指往外（6K 三押 J K L，8K 四押 J K L ;），不够的从另一只手的食指往外补；
      优先右手（多押用手选另一只手时左手），那只手来不及才换；一块双押砖要按超过 4 下时补到 min(下数, 键数)（`ChordPresses`）
    - 让手的单押放另一只手的食指，前一下先让到中指（同 4K）；另一只手刚按过多押来不及、后面的多押又紧挨着时，这一下放偏好的手，让多押换手（复现 TUF 298）
    - 手指歇够（`RestFingers`，`NotePlanner.Rest.cs`；同一天用户截图 Hello (BPM) 2023：右手刚按完 J+K 双押，隔一下 30 ms 又要按 J）：上面的规则只管和上一下不连按，
      排完再顺一遍，每一下按「这根手指上次松开到现在歇了多久」算代价（歇不到 R/2 很大、R/2–R 一点点、超过 R 没有），加上离规则排的那根手指多远
      （同一只手近、另一只手远）、换过去后的 21 式、长按那只手、和前后两下的距离（跳轨小、孤立音符大）。单押在所有键里挑代价最小的（轮指关掉时只在两根食指里挑），
      一只手的多押在两只手的相邻几根手指里挑（从食指起往外挪一根加一点）。规则排的手指歇够了就不动；为了歇够而换的位置不许造成孤立音符、
      不许占掉紧接着那一下的键（规则排的位置已经连按了才放宽）
    - 外轮（`OuterFirstMany`，外轮、轮指开着时）：同一只手 R 以内连着两下从内往外的换位置，变成从外往内；会连按、换过去的手指没歇够 R/2、
      和前后又成 21 式、附近多出孤立音符的不换
    - 左撇子最后按 `键数 − 1 − 轨道` 镜像，规则仍只写右手一份
    - 4K 逐音不变：改动前后用 `tools/DumpPlans.cs` 转储工坊和 TUF 校准谱 867 张 × 38 种设置，逐字节相同。`ManyKeysTests` 守着新规则的例子和硬约束
      （提示和分组同 4K、单押一个键、长按跟着砖、双押同手、左撇子是镜像、连按和孤立音符加起来不比 4K 多），也在本机真实谱上跑（工坊全部、TUF U10 以上）。

## 节拍线和小节（`BeatGrid.Infer`，`BeatInference.cs`）

四轨面板、太鼓条的节拍线和手序编辑器的小节线、小节号都来自这里（Mod 写进会话的 `beats`，格式 `[秒, 是否小节线]` 没变）。只用来画：排键、难度估算都不看节拍线。
2026-11-19 玩家反馈编辑器自动分的小节不聪明。原来的做法（`MusicalTempo` + `Build`）把 2 的整数次幂以外的变速都当成换了 BPM、每次都从变速点重新起小节；
冰与火之舞的关卡 BPM 又常是谱师为转角设的数（工坊 2802147583 按关卡变速算出 32352 BPM，每秒 90 条线）。参考 Malody（拍全曲连续累计、BPM 点只换算时间、小节线是叠在上面的一层），改成拍和小节分两层：

1. **主 BPM**：关卡的变速段按「差 2 的整数次幂算同一类」归类，按持续时长选最长的一类；八度取这一类里关卡用得最久的那个 BPM（60–300 内），不在就折进 100–200。
2. **关卡 BPM 和砖块对不上时从砖块推**：一段里的砖用关卡 BPM 的拍网只对得上不到六成（比如 64.711 BPM 配 182° 的砖），拿最常见的几种间隔试它的倍数、简单分数，九成以上落在拍网上才用（`BeatSource.Tiles`）。
3. **每段的速度**：主 BPM 那一类只是疏密；4 段、8 拍以内就回到原来速度、回来时落在拍网上的是写法（伪双押、挤进一拍的连打）；和现在的拍子成简单比例、砖块对得上的是连音写法；一块砖一个速度、再用转角把时间补回来的（往后看两拍也对得上）也接着用原速度。都不是才算真的换了速度，用这一段的 BPM 折到离现在最近的八度。
4. **拍子连续数**：换了速度时这一拍剩下的部分按新速度走完，不在变速点重新起。只有换了速度、或变速点不落在拍上时才检查：换个拍点（这一段第一拍里的砖之一）后，整拍、半拍上的砖（重音加权）比接着数多三成以上，才从这里重新起拍、重新起小节。一块砖一个速度的加速段看不出来，接着数。
5. **小节起点**：每一组（重新起小节之间）挑 4 拍里哪一拍是第一拍：落在那一拍上的重音（多押、长按、隔了一拍半以上后的第一下）加起来最多的；分不出来（差不到一成）时从第一块要按的砖所在的拍起。每小节固定 4 拍，没有拍号。

拍网：1/64 以内的细分（一格不短于 6 ms），误差不超过 2 ms 和一格的 3%；相隔 12 ms 以内的两下当作同时按。

|---|---|---|---|---|
| 工坊 26 张 | 9 张 → 0 张 | 4 张 → 0 张 | 1128 / 8527 → 10 / 3162 | 93.5% → 99.4% |

## 实际 BPM（Core 的 `RealBpm.cs`）

2026-11-26 玩家（QQ 群）：BPM 框显示的是砖块 BPM（起始 BPM × 砖块速度倍率 × 歌曲变速，`GameReader.CurrentBpm`），即转半圈的速度；转角小的砖一下不到一拍，打雪花时看不出实际按多快。用户选了方案 A：大号数字不变，在「BPM」字样左边加一行小字。

- **算法**：60 ÷ 将要按的音符（`NextNote`）与上一个音符的时间差，再乘音乐播放速度（音符时间是歌曲进度，变速后真实间隔要除以 pitch）。以排好的音符为单位，所以多押、伪多押、双押砖都算按一下
- **不显示**（写 -）：还没按第一下、已经按完、两下隔了超过 2 秒（`RestSeconds`，否则停顿后那一下会显示二三十）
- **不平滑**：每按一下才变一次，匀速段本来就不跳；附点、三连这种长短交替的节奏会跟着交替，这是实际情况
- **设置**：`ShowRealBpm`，默认开，收在外观页「BPM 与剩余时间」下面；演示里也显示（菜单音乐按它的 pitch 算）

## 几个容易踩的坑

- **只引用游戏里有的程序集**：游戏里只能加载 `Managed` 目录里有的程序集，新加引用先确认游戏里有。编译后看 DLL 实际引用了什么（Windows PowerShell 5.1）：

  ```powershell
  [Reflection.Assembly]::ReflectionOnlyLoadFrom((Resolve-Path src\RhythmHint.Mod\bin\Release\RhythmHint.dll)).GetReferencedAssemblies() | Sort-Object Name | Format-Table Name, Version
  ```

  现在（2026-11-19）是 mscorlib、System、System.Core、System.IO.Compression、Newtonsoft.Json（游戏自带，读翻译表和手序文件）、Assembly-CSharp、Assembly-CSharp-firstpass、UnityModManager，
  和 Unity 的 CoreModule、IMGUIModule、TextRenderingModule、InputLegacyModule、AudioModule、ImageConversionModule、UIModule、UnityEngine.UI、UnityWebRequestModule（自动更新下载），版本号都和游戏里的一样，只有一个例外：
  System.IO.Compression（自动更新解压，`ModUpdate`）引用的是 net48 参考程序集的 4.2.0.0，游戏 Mono 带的是 4.0.0.0。Mono 加载框架自带的程序集时按游戏里的版本来，游戏里实测能解压（验证记录「1.3.0 之后」自动更新一行：已装好 9.9.9（14 个文件））；
  以后游戏换了运行时再验一次。RDTools、netstandard 只在编译时需要，DLL 里没有对它们的引用。
- **RDTools.dll**：`ADOBase` 的基类在这里，编译必须引用。
- **在游戏里打开网页**：不要直接用 `Application.OpenURL`。浏览器原本没开着时它会成为游戏的子进程，Steam 把游戏启动的程序也算作游戏，退出游戏后浏览器不关，Steam 一直显示「停止」（2026-11-17 实测：关掉浏览器才停）。用 `Browser.Open`：Windows 上交给 `explorer.exe` 转给系统外壳去开，只开 https 地址。
- **angleData 有 N 项就有 N+1 块砖**，按键 N 次。
- **伪双押 / 伪多押**：官方关卡用两块相隔约 25 ms 的砖表示双押，必须合成一个提示，否则会画成「双押 + 旁边多一个单押」。
  三押是三块串着来（每块隔二三十毫秒），只和第一块比时间会漏掉第三块，所以按相邻两块的转角串起来（排键规则第 11 条）。
  这个提示在第一块和最后一块砖的正中间到判定线（`HintTiming`；手序编辑器 model.js 音符的 `time` 同样画在正中间，两边一致）。2026-11-25 用户：多押每次跟着提示准确按下，总是稍早或稍晚。原来放在第一块砖上，一次按下几个键时后面几块总是按早。排键和手序文件仍用第一块砖的时间（`PlannedNote.Time`）；编辑器的间隔、几分音符和连按也用第一块砖的时间（`start`）。
  同一天用临时按键日志让用户把同一首 532 BPM 的谱（伪双押两块隔 18.8 ms）各打一遍对比正中间和四分之一处：玩家跟着提示按，四分之一处整组提前约 7 ms，第二块砖平均早 18 ms、太快从 9 个变 14 个；正中间两块砖是 +1 和 −8 ms，最均衡。多押后紧跟的那一下两遍都晚 15–18 ms，和提示位置无关（玩家按 J+K 是轻轻一滚，约 10 ms，下一下从滚完那一下数起），所以留在正中间，别再挪。
  提示要等最后一块砖按到才消失；过了提示时间、还在等后面的砖时音符停在判定处（`OverlayFrame.TimeTo`），不然会微微越过判定线 / 判定圈，看起来像漏按（用户录屏，圆形样式和太鼓条上最明显，横条越过的那截被按键框盖住）。双押砖（Multitap）只有一块砖，提示时间不变。
- **死亡后**：`songposition_minusi` 还在走，用 `DisplayClock` 在 Fail / Fail2 状态定住画面。游戏状态直接读状态机（`stateMachine.GetState()`，还没初始化时是 null，退回 `currentState`）：`scrController.currentState` 是它 `Update` 里抄过来的，关卡编辑器里不更新（1.2.0 实测编辑器里播放、死亡后都还是 None，死后音符照走），游戏自己的失败处理（`Fail2Action`）也是看状态机。
- **歌曲进度每帧走得不匀**：`scrConductor.Update` 里音频时钟（`AudioSettings.dspTime`）没变时按帧时间往前推，一报新值就直接对齐（2026-11-19 反编译 Unity 6000.3.25 版核实），那一帧多走或少走大半帧。
  本机 300 Hz 显示器、不锁帧（约 320 帧/秒）实测：音频时钟每秒报 100 次，原始进度每 5 秒有约 440 帧的误差超过四分之一帧（P95 3.7 毫秒，比一帧还长），提示看着像没跑满帧数。
  画面因此不直接用它：`SmoothSongClock` 按真实帧间隔 × `song.pitch` 往前走，再把差慢慢收回（时间常数 0.1 秒）；差超过 50 毫秒（回检查点、跳转）、一帧超过 0.1 秒、暂停、进度停住超过 50 毫秒时直接用游戏进度。
  平滑后 P95 误差 0.14 毫秒、超过四分之一帧的 0 帧，和原始进度平均差 0.00 到 −0.07 毫秒（判定线位置不变）。设置页演示没有菜单音乐时直接读音频时钟（约 10 毫秒才动一下），画面同样走这个时钟，嗒声仍按原始音频时钟排。
  画面板本身每帧只花 0.2–0.3 毫秒，不影响帧率。
- **编辑器残留的通关 / 失败状态**：编辑器播放完后状态留在 Won / Fail，下次播放不会清掉。所以编辑器里每次开始播放时记下当时的状态，
  这次播放中状态变过以后才算通关 / 死亡（Core 的 `PlayStateTracker`，有单测）：否则第二次播放一开始就被当成「本关结束」；上一次死了留下 Fail、这次先回到开始再死，也要认出这一次。
- **暂停时收起**：关卡里 `scrController.paused` 为真时面板按出场动画收起，游戏画面和界面文字（含暂停菜单）跟着面板一起放大回全屏，不挡暂停菜单；继续后再一起滑入、缩小。
  面板完全收起时界面正好和原样重合，这时才改回覆盖模式，看不出接缝。暂停中打开本 Mod 的设置窗口时面板照常显示，方便看改设置的效果，
  界面文字（含暂停菜单）也跟着一起缩小。
- **入场 / 出场动画（`PresenceAnimator`）**：两个方向都是缓出（一开始就走得快）。原来出场是入场曲线倒着走（先慢后快），
  按 Esc 后面板在原地停约 0.2 秒才滑走，而暂停菜单已经全屏出现，看起来不连贯（录屏逐帧确认）。中途反向时从当前位置重新起一段，不跳。
- **编辑器的状态**：编辑器走自己的流程（`scnGame.Play` → `Start_Rewind`），`currentState` 不更新（早先实测一直是 Start，1.2.0 实测一直是 None），所以编辑器里以 `scnEditor.playMode` 判断是否在播放（暂停在播放中也算），通关 / 死亡改读状态机（见上面「死亡后」）。
- **自适应游戏画幅：游戏画面**（设置「自适应游戏画幅」，`Settings.ShrinkGameView`）：面板出现时按动画进度把所有 `targetTexture == null` 的摄像机的 `Camera.rect` 缩到面板让出来的区域（`GameViewport` + Core 的 `ViewportShrinker`）。

    转换时把 `dynamicPixelsPerUnit` 设成覆盖模式下的缩放，还原时改回原值。
  关卡里始终跟着面板缩放（暂停、开关本 Mod 设置窗口、本关结束都一样），离开关卡后面板还在滑出时也继续跟着，滑完才改回覆盖模式。
  曾经在「暂停」或「本 Mod 设置窗口开着」时直接改回覆盖模式，和面板动画对不上：关窗口那一帧界面先跳成缩小再随面板放大（录屏逐帧确认），已去掉这些例外。
  每帧找一次新出现的画布；收起时改回覆盖模式。游戏期间自己改过模式或摄像机的画布保持游戏的值。自己的挡板画布不动；IMGUI 画的字管不到。
  每种画布第一次被缩时在 UMM 日志记一行（名字、层、排序、缩放），方便对照。
- **摄像机改画贴图（0.9.0 修的花屏）**：游戏在关卡、选关里用 `scrCamera.SetupRTCam(true)` 让三个摄像机先画到一张 RenderTexture，再由 Overlaycam 整体显示；
  编辑器里又切回直接画屏幕。被缩过的摄像机切到画贴图后如果不还原，贴图里只有缩小的那块有画面，其余是没清过的显存，显示出来是一大片彩色花屏。
  现在每帧先把「缩过、现在画到贴图上」的摄像机还原（包括被禁用、手动渲染不在 `Camera.allCameras` 里的）。
- **长按**：长按砖结束那块是按住到底自动落上的，游戏里这时再按会被忽略（`scrPlanet` 里前一块是长按时直接返回，严格长按还记「太早」），所以不算一次按键。下一块也是长按砖时不一样：`scrPlayer.UpdateHoldBehavior` 里松开不打下一块，`UpdateHoldKeys` 里按键才打，所以连续的长按砖每块都要按一下、各自按住到下一块（`FloorHits`；2026-11-20 用户录屏：原来合成一条，照提示按住，过了第二块一拍左右就死）。
- **编辑器的砖块**：编辑器自己用 `scnEditor.floors`，即 `customLevel.levelMaker.listFloors`，编辑器里只读这一份。
  `ADOBase.lm`（`scrLevelMaker.instance`）按场景缓存：从主菜单直接进编辑器时它指向另一份列表，读出来一块要按的砖都没有、之后也不再变（0.9.0 前编辑器自动播放因此一直不显示）。
  其余场景先用 `ADOBase.lm`，取不到再用 `customLevel.levelMaker`；判断对象是否已销毁要用 Unity 的 `==`，`?.` 判断不了。
  关卡指纹里含砖块列表本身（`RuntimeHelpers.GetHashCode`），换了一份列表就会重排。一块要按的砖都没有时不显示，并在日志里写出各类砖（已销毁 / 自动 / 中旋 / 假砖 / 长按）的数量。
  不再要求 `controller.gameworld`（自由移动段会被设成 false）。选关界面（`isLevelSelect`、`isCLS`）不显示。
- **netstandard 2.1**：Unity 6 的模块按 netstandard 2.1 编译，要引用游戏目录里的 `netstandard.dll`。
- **AudioClip.SetData**：Unity 6 有 `ReadOnlySpan` 重载，net48 编译环境没有这个类型，嗒声改用读取回调生成。

## 日志

用 UMM 自带的 Logger（分 Log / Warning / Error），写进 `Managed\UnityModManager\Log.txt`，每次启动游戏重写。日志一律是中文（给开发者看），不跟界面语言走。
每次排键会记一行状态（按键次数、提示数、双押数、各轨使用次数）；画面显示 / 隐藏切换时记一行原因（例如「画面：隐藏（游戏状态 Start）」），查「为什么没显示」先看这里。
运行中出现意外异常会记完整堆栈并停用叠加层，避免每帧刷日志。
